# Considered and set aside

## In short

Ten routes were tried or weighed and are not pursued. Seven fail on what the game lets a mod do; two (swapping every cargo type's price function, and a step instead of a straight line) are choices not made; one (booking the adjustment after the game pays in full) worked and was replaced by ticket billing. They are listed so they are not rediscovered: each row gives the reason, and "Revisit if" says what would make us look again. The facts behind them are in [findings](../findings.md).

| Idea | Why not now | Revisit if |
|---|---|---|
| **Change pay in the income function** (`cargoIncomeScript`) | It gets only the difficulty factor, the price factor and the distance, never the unit's age. Only one mod can replace it, so it also invites conflicts. | The game passes the unit (or its age) to the function. See [needs-game-support](needs-game-support.md). |
| **Redirect a cargo type's price function at run time** (`scriptRef` through `api.res.cargoTypeRep`) | Readable, but changing it had no effect. | The game starts honouring changes at run time. |
| **Swap the price function of every cargo type at load time** for one that decays with delivery time | A global rewrite of cargo definitions: the heaviest footprint, and it conflicts with any other mod that adds or changes cargo types or their price functions (last one wins). Not tried, and not needed while the ticket price answer works. | The ticket price answer turns out to be unworkable, or a conflict-safe way to extend a cargo type appears. |
| **Read the vehicle's pending income at unloading** (`unloadPendingIncome`) | Nil at the time of the arrival event, and there is no command to change it. | The game exposes pending income in the event, or a command to scale it. |
| **Share a global between the income function and the game script** | The two run in separate scripts, so a module-level value is not shared. | A supported channel between them appears. |
| **Show the deduction in the vehicle's logbook** | The logbook holds counters (items transported and the like), not money, and journal entries carry no text. | The logbook gains money fields or journal entries gain a note. |
| **Book the adjustment to the player's account after the game pays in full** (the bookings) | It worked (the entries landed in the balance exactly, bonuses and full deductions alike), but the vehicle and line windows kept showing the full pay, each entry rested on a pay prediction good to about 1% per unit, and it needed a queue sent from `update`. The ticket price answer does the same inside the game's own pay, so the bookings were removed from the code. | The ticket price event stops scaling pay. |
| **Book each deduction to the first vehicle and line of the unit** (bookings) | The game pays a delivered unit once, at the consumer, and shares the pay along the chain by an unknown formula, so the first leg is the wrong ledger for any transferred cargo (road cargo 13 got 0.05 of its predicted pay while the rail vehicle got 3.6 times). It also crashed when a vehicle in the chain had been sold. | The split formula is known or exposed. See [revisit-later](revisit-later.md). |
| **Send a booking with a result callback from `update`** | The engine refuses it ("Callbacks are currently disallowed"). Bookings go out without a callback and success is judged from the balance. | The restriction is lifted. |
| **A step instead of a straight line for the pay curve** | A unit just either side of a step would differ by up to half its pay, and many deliveries sit near the 30 to 50% freshness range. | Players ask for it as an option; it needs no new mechanism. |
