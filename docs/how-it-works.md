# How it works and where it can over-penalize

## In short

- **What it does.** The game pays every delivered cargo unit in full. The mod then works out how fresh the unit was and books one correcting entry to the player's account: a bonus for fresh cargo, a deduction for slow or spoiled cargo, nothing at the break-even point. The mod never changes the game's own pay.
- **What drives the result.** Freshness (how much of the unit's spoil limit was used), the curve settings (set in game and kept in the save), and the mod's prediction of what the game paid for that unit (price x distance x the Cargo Income setting x the company's ticket price multiplier).
- **Where it can over-penalize.** Three places, all small or rare. The prediction is good to about 1% on average (a single unit can differ more, see below), so a full (-100%) deduction can take a hair more than the unit paid. A unit flagged spoiled by the game takes the full penalty whatever its age. Cargo that waited in a warehouse is judged on a corrected age, and if that correction were wrong it would over-penalize (the code keeps a `formula` mode to compare, see [stored-cargo-modes.md](future/stored-cargo-modes.md)).
- **Where it under-penalizes instead.** A unit whose source or target building cannot be found (sold or rebuilt in transit) gets no entry. Units paying less than 1 money get no entry. Pay the game gives beyond the prediction is not adjusted.
- **How sure we are.** The prediction matches the player's ledger at 1.001 on both flat saves (earned rank 1 and 2), and individual vehicles range between 0.92 and 1.21 (their share of a chain's pay). Bonuses and deductions land in the account as booked. A -100% deduction has been run in the game (QZZZ, 2,850 spoiled units, each deducted 99.99% to 100.01% of its predicted pay).
- **Side effect to know.** With the default -100% penalty a save that spoils a lot can drive the account negative (QZZZ went to -$7.9M in one run). By design the mod does not cap deductions at the balance (a spoiled unit pays nothing, and a rounding-sized fine is accepted); see [future/revisit-later.md](future/revisit-later.md).
- **Unknown.** How the game splits the pay of a transferred unit along its chain (the mod books to the player, not to vehicles or lines), why player income exceeds the prediction on some saves, and whether the 1% prediction error is random or biased.

## The steps

1. The game pays a unit when it arrives, in full, using the income function. A mod cannot see freshness at that point, so the pay stays as it is.
2. The mod receives the arrival event, which carries the unit's pickup time. The unit's *spoil limit* is the game's adjusted delivery time for its cargo (`api.engine.util.stock.getAdjustedDeliveryTime`, the limit the vehicles' cargo bar runs against): It shrinks as the game years pass: 1.5 x the cargo file's delivery time in 1900, 1.4 x in 1916, about 0.75 x by 2191 ([findings](findings.md)). If that call fails the mod falls back to 1.5 x. Freshness is `1 - age / spoil limit`, where age is the time since pickup (for stored cargo, minus the paused time). 1 is just picked up, 0 is at the spoil limit, below 0 is past it.
3. The curve turns freshness into a share of the unit's pay: `+bonusPercent` while at or above `bonusDownToFreshness`, a straight line down to 0 at `breakevenFreshness`, a straight line on to `penaltyPercent` at `penaltyBelowFreshness`, and `penaltyPercent` below that and for spoiled units. The five in-game settings behind these names are described in [changing-settings.md](changing-settings.md).
4. The mod predicts the unit's pay from the construction positions of its source and target, scaled by the Cargo Income setting and the company's ticket price multiplier, both read at run time. At rank 1 the multiplier does not exist and the mod uses 1.0.
5. The adjustment is the curve share times the predicted pay, rounded to whole money. A deduction is capped at 100% of the predicted pay. The mod queues it and the game script's `update` books the sum per carrier for the player's account.

The curve comes from the mod's in-game settings: six settings in `mod.json` (five for the pay curve, one for the stale threshold) that the game shows under Mods, in New Game and in Load Game, stores in the save and hands to the game script as list positions (1-based; the `numbers` field is not passed, so the script turns positions into values itself). The game script reads them again on each load, so a player can retune a save by changing them in Load Game before loading. A save with no in-game settings (from before they existed) gets the settings' defaults from the game, in the dialog and in the script, so it plays on the default curve until its player sets one; `settings.tl`'s curve is only a fallback for when the game hands over no settings at all. The log shows the source in `BEST_BEFORE curveSettings source=params|settings.tl ...`, written when the source or the numbers change. `logLevel` is not an in-game setting and comes from the file. Checked in the game with probe settings (positions, 5% steps, edit on load, and the dialog showing the save's own values) and with the real five settings on new games (defaults, out-of-order and in-order values) and on one old save without settings.

Ranges the mod enforces: bonus 0 to +200% (a unit can pay 3x in the full bonus window), penalty 0 to -100%, freshness points in the order 1 >= bonusDown >= breakeven >= penaltyBelow >= 0. Values outside are clamped. The in-game sliders cannot leave their ranges; when the freshness points are out of order the mod lowers the later ones and the `curveSettings` line says `adjusted=yes` (at any log level but `off`). A range clamp of the `settings.tl` fallback curve is not logged.

## Where it can over-penalize

- **Prediction error.** The mod does not read the pay the game gave; it rebuilds it. That is good to about 1% on average, but a single unit can differ more (derived pay over predicted pay ran from 0.92 to 1.21 across vehicles; the likely reason is that a chain's pay is shared among its vehicles by a formula we do not know, which we have not confirmed). With a -100% penalty the deduction equals the predicted pay, so a prediction a little too high leaves that unit a hair negative. The effect is small.
- **Spoiled units.** The game's own "good" flag decides what is spoiled. A flagged unit always takes `penaltyPercent`, even if its computed freshness looks fine. For cargo that did not wait in a warehouse the flag and the formula agreed on all 82 units checked on the small save; for the other saves the check has not been made unit by unit.
- **Stored cargo.** A specialized warehouse pauses a unit's spoil timer, so its plain age overstates how old it is. The mod takes the paused time (`deliveryExtensionDuration`) off the age (the `corrected` mode, the only one offered). On the large flat save, 132 units that went rail to warehouse to road had a plain freshness near -0.45 but the game flagged them good, and corrected they scored about 0.65 and earned the full bonus. Judged on plain age they would have lost about $5.7M of $66M base pay. The other modes (`formula`, `zero`, `neutral`) are kept in the code to compare, see [stored-cargo-modes.md](future/stored-cargo-modes.md).
- **Where the entry goes.** The adjustment is booked to the player only, not split along the unit's chain. The game's per-vehicle and per-line balances still show the full pay, so they overstate a vehicle's earnings when a deduction applies, and the player's balance is the one to trust.

## Where it under-penalizes or misses

- **Missing entities.** The mod guards every lookup. If a vehicle, line or building is gone, the unit is skipped for the lookup it needs; this loses an adjustment, it does not add one.
- **Pay beyond the prediction.** Pay the game gives beyond the prediction is not adjusted. Player income ran above the prediction on some saves (see [findings](findings.md)); the cause is unknown (passenger income is not logged).
- **Small units.** Adjustments below 1 money are not booked.
- **Passengers.** Passenger income is not part of the mod at all, only cargo.

## Evidence

- QZZZ, +30%/-100% curve: 7,921 units, 2,850 spoiled, each deducted its whole predicted pay (ratio 0.99988 to 1.00009), none beyond rounding; the player ratio is 1.575 there because that save has income the prediction does not cover, so it says nothing about the margin.
- Flat large save, rank 1, Inflation High, +50%/-95% curve: 1,572 units, all sent, derived/predicted pay 1.001 at player level, 99% of booked entries landed as exact steps of the balance.
- Second flat save (potential level 2): 1.001 over 2,289 units, see [findings.md](findings.md).
- Curve replays across the saved runs: [future/revisit-later.md](future/revisit-later.md).
